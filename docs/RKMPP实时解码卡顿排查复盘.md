# RKMPP 实时解码卡顿排查复盘

场景是 Ubuntu 上的 SRS 发布 640×480、30 fps 的 H.264/RTMP 输入。RK3588 上的 AlertGateway 拉流、解码、推理，再把结果推回 SRS。最初看到的是回推画面卡顿、帧率偏低，早期还出现过花屏。

## 怎么发现并定位

1. **先确认真正跑起来的解码器。** 板端日志报 `missing hardware decoder h264_rkmpp`。这表示应用当时加载的 FFmpeg 无法按名字找到该解码器。板上存在 MPP 运行库，只说明系统具备其中一项依赖。用板端 SDK 的 FFmpeg 4.4.1 构建带 RKMPP 的部署包，再用启动日志中的 `decoder=h264_rkmpp` 确认实际选中的解码器。应用查找解码器的位置见 [PullStreamThread.cpp:185](../src/capture/PullStreamThread.cpp#L185)。
2. **硬解启用后，回推仍只有约 6–10 fps，于是看调用耗时。** 在仍使用 100 ms 超时、取帧更积极的中间版本上，板端记录到取完可用帧后，下一次取帧常接近 96 ms。30 fps 每帧间隔约 33 ms，一次近 100 ms 的等待就会跨过三个帧间隔。这里的 96 ms 是当时的板端观测值，100 ms 是源码里的单次底层取帧超时设置。
3. **沿应用调用追到 FFmpeg 的 RKMPP 适配层。** 应用在同一个拉流线程内交替调用 `avcodec_send_packet()` 和 `avcodec_receive_frame()`。当适配器进入 MPP 的 `decode_get_frame()` 且暂无输出时，应用必须等当前调用返回才能继续送包。旧版还有一条包所有权问题：适配层尝试提交后立即解除输入包引用，即使底层返回 `EAGAIN`，该包也无法留到下次重试。源码入口见 [PullStreamThread.cpp:282](../src/capture/PullStreamThread.cpp#L282)、[PullStreamThread.cpp:294](../src/capture/PullStreamThread.cpp#L294) 和 [补丁中的旧送取逻辑](../tools/ffmpeg/4.4.1-rkmpp-backpressure.patch#L59)。
4. **改动后再看实际回推帧率。** 适配层把单次取帧超时从 100 ms 改为 1 ms。MPP 暂时收不下包时，保留待提交包，尝试取出输出，再重试提交。最终版本实测回推约 29.9 fps。见 [超时修改](../tools/ffmpeg/4.4.1-rkmpp-backpressure.patch#L7)、[待提交包的重试逻辑](../tools/ffmpeg/4.4.1-rkmpp-backpressure.patch#L86) 和 [构建与部署记录](rkmpp-deployment.md)。

## 面试口述版（约一分钟）

> 我在 RK3588 上调一条 30 fps 的实时视频链路，SRS 收到的结果流明显卡顿。第一步是核对板端实际加载的解码器。日志显示找不到 `h264_rkmpp`，所以我先用板端 SDK 的 FFmpeg 构建带 RKMPP 的版本，通过日志确认硬解实际启用。
>
> 启用硬解后回推还是只有约 6 到 10 帧。我看解码调用耗时，发现取完已有画面后，下一次取帧经常花近 100 毫秒。顺着 `avcodec_receive_frame()` 追到 MPP 适配器，发现取帧允许等 100 毫秒。送包和取帧在同一线程，取帧没返回，下一包就送不进去。我还看到旧适配器在 MPP 拒收时没有保留待重试的包。
>
> 我把单次取帧等待缩到 1 毫秒，并让待提交包在遇到背压时保留，先尝试取帧再重试。上线验证时，SRS 结果流恢复到约 29.9 帧。两个改动一起验收，所以我可以确认组合修复有效，单独缩短等待能恢复多少帧率还需要做对照。

## 面试追问

- **为什么看到 MPP 库，还要检查 FFmpeg？** MPP 是底层接口，应用通过 FFmpeg 的解码器注册表查找 `h264_rkmpp`。能找到库、能找到解码器、运行时实际选中解码器，是三个可分别检查的环节。
- **为什么不在应用里用两个 `while`，先送包再取帧？** 批量送已有包可以减少碰到空输出队列的机会。取帧循环最后一次调用仍由后端决定是否等待。应用线程正在等底层取帧时，它无法继续向 MPP 送包。
- **有没有证明花屏和低帧率来自同一处？** 最终版本里两种现象都消失了。近 96 ms 的取帧记录解释了当时的吞吐损失。花屏没有做码流或逐帧对照，缺少独立根因证据。
- **重做实验怎么验证得更严谨？** 用同一输入和相同取帧策略，分别测试原策略、只缩短超时、只处理背压、两者都改。记录取帧耗时分布、近 100 ms 调用次数、MPP 拒收和重试成功次数、SRS 实际帧率及帧间隔。
